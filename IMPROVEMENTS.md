# OMGS field test improvements

Source: six traced reviews run on 2026-10-16 against projects listed on Awesome Intune. No sandbox proof tier was used, so no record below is confirmed. Sensor: gitleaks on every target. All target worktrees were left clean.

## Review results at a glance

| Project | Type | Records | Strongest traced candidates |
| --- | --- | --- | --- |
| Edge Favorites Builder | static web app | 2 needs validation, 1 rejected | URL schemes flow into enterprise policy exports unchecked. Imported files parsed with unbounded nesting. DOM injection lead rejected: every render path escapes. |
| Intune Drive Mapping Generator | ASP.NET web app | 3 needs validation, 1 rejected | JSON configuration is string-replaced into a single quoted PowerShell literal, so an apostrophe in a value breaks out. Imported UNC paths can reach PowerShell expression expansion. Unsupported group filters can become unrestricted mappings. |
| Apple Compliance Version Updater | PowerShell scripts | 3 needs validation, 1 rejected | The SOFA feed can move a compliance minimum backwards: the update path compares only for equality before writing the feed derived target, in three runbook copies of one root cause. |
| win32-toolkit | PowerShell module | 3 needs validation, 1 rejected | Sandbox capture exposes host project files to installer writes. Hyper-V result extraction does not enforce requested host output paths. A captured top level application directory can become a shared root cleanup target. |
| Deployment Editor | desktop app | 4 needs validation | Imported MSI metadata and action parameters are emitted as interpolating PowerShell source. An upload plugin runs Invoke-Expression on an assignment taken from a project supplied script. Project folder names reach an elevated PowerShell command without literal escaping. |
| AppPruner | Swift CLI | 3 needs validation, 1 rejected | Manifest app names are interpolated into a zsh command that runs even in dry run mode. Deletion paths can be formed through a user controlled parent symlink. Homebrew detection executes the brew binary before switching to its owner. A download integrity lead was rejected: digests are checked. |

Pattern across all six: the dominant risk shape in this ecosystem is not web authorization. It is values becoming code (generated PowerShell and shell strings), untrusted input becoming enterprise policy, and privileged local file operations. The current v0 packs would have missed most of these candidates.

## P0: correctness and trust

1. Stack and surface detection in audit init. Detect at least static HTML and JavaScript, ASP.NET, PowerShell scripts and modules, Swift tools, and binary heavy repositories. Seed ledger units from real entry points and sinks per language. The current fallback unit (whole repo, web authorization classes) was wrong for six of six field targets.
2. First party versus vendored code separation. Deployment Editor carries hundreds of vendored binaries and minified libraries. OMGS must inventory first party source, exclude vendored paths from hunting and sensor noise by default, and state exclusions in coverage. Gitleaks flagged the vendored code editor twice and nothing real.
3. Run sensors, do not just detect them. Execute available deterministic tools during init or check, ingest results as candidates with redaction, vendor aware baselines, and stable identities.
4. Report renderer parity with the designed one pager. Show verdict counts, rejected records with their counterevidence, needs validation evidence next to each intent question, sensor results, examined and not examined coverage from the ledger, and run metadata. Today a human must read findings.json to see most of the actual review.
5. One root cause, many locations. The Apple updater produced three records for one copied defect. Support grouped findings with multiple locations, or a family identity above the per location fingerprint, so counts and metrics stay honest.
6. A sandbox backend that exists on user machines today. Every strong candidate in this test is stuck at traced because no executor was available. Ship OS native backends behind the existing sandbox interface so proof tests can actually run, with the report naming the backend used.
7. Run directory hygiene. Create run output with owner only permissions and warn when the output path sits under a shared temp directory. Reports describe vulnerabilities in other people's code.

## P1: packs and hunting quality

8. Generated script safety pack. PowerShell single and double quoted interpolation, subexpressions, apostrophe breakout from serialized JSON, Invoke-Expression on parsed input, shell string interpolation versus argv execution. Four of six targets produced candidates here, including one literal Invoke-Expression on project supplied text.
9. Feed and import to policy pack. External feeds and imported files that write enterprise policy need monotonicity guards (never lower a security minimum automatically), fail closed handling of unsupported filters, and provenance checks before a write.
10. Privileged local operations pack. Deletion through symlinks, path allowlists for recursive removal, executing binaries from user writable locations before dropping privilege, guest to host file extraction, and sandbox shares that expose host project files to guest writes.
11. PowerShell as a first class language. The Intune ecosystem runs on it: three of six targets were primarily PowerShell and a fourth generates it. A PowerShell pack likely outranks a second TypeScript framework for this audience.
12. Enforced hunter and verifier separation. In this test hunters wrote final verdicts directly and verification was manual spot checking. The CLI or skill flow should require a distinct verifier pass per candidate and record who verified what in run metadata.
13. Ledger update tooling. Hunters need commands to move units between planned, candidate, covered and blocked with evidence links, plus a coverage critic step. Free form architecture notes should not be the only coverage record.
14. Structured prerequisites. Attacker prerequisites currently live in evidence prose with inconsistent quality. Add a dedicated field so triage can sort self inflicted cases from cross principal ones mechanically.

## P2: workflow and ecosystem

15. One command repo review. Clone shallow to scratch, init the run, run sensors, detect the stack, and print a ready made agent brief. This test repeated those steps by hand six times.
16. Batch mode for curated lists. Queue many repositories, keep one run directory each, and render an aggregate index with per repo counts, blockers and cost. Directory scale security scanning is a natural OMGS deployment.
17. Benchmark cases from real reviews. Several traced candidates convert cleanly into proof tests once a sandbox exists: an apostrophe in a drive mapping value must stay data in the generated script, and a dry run must never execute a manifest controlled shell string. Adjudicated field cases beat synthetic vulnerable apps for this ecosystem.
18. Model routing resilience. One frontier model refused security review work mid task during this project. Per role model selection with recorded fallbacks turns a refusal into a reroute instead of a stalled run.
19. Local run accounting. Record model identity, agent calls, wall time and cost per run in run metadata by default. The benchmark design needs these numbers and hunters currently ignore budget fields they are not forced to update.
20. Intent question library per ecosystem. Recurring questions from this test (may a feed lower a security minimum, who may supply a manifest, which URL schemes may reach managed browsers) should ship as reusable intent prompts that resolve into policy once.

## Implementation status after the 2026-10-16 rerun

Implemented and re-verified on the same six targets: item 1 (stack detection seeded the right primary stack on six of six, with a minor Python false positive on the Swift target), item 2 (472 of 636 Deployment Editor files classified vendored and both gitleaks hits flagged vendored), item 3 (sensors execute during init and check, with secret values redacted out of retained output), item 4 (reports grew from under 1 KB to 3 to 15 KB with rejected evidence, pending evidence, coverage, and sensor lines), item 5 in report form (family field plus family counts; the three copied rollback records group into one family), item 6 (OS native Seatbelt backend verified: scratch write allowed, outside write denied, network denied, timeout enforced; bubblewrap path exists for Linux but is untested on this machine), item 7 (run directories are owner-only with a shared-temp warning), items 8 to 11 (four new packs: generated script safety, feed to policy, privileged local operations, PowerShell), item 13 in basic form (`omgs ledger set`), item 14 (`prerequisites` and `verified_by` fields), item 15 (`omgs review` clones and initializes in one command), item 17 as documented case candidates in benchmark/field-cases.md, and item 19 in basic form (run metadata now records stacks, file counts, start time, hunter and verifier fields).

Still open: item 5 as a full multi-location finding model, item 12 enforced verifier workflow in the CLI, item 16 batch mode, item 18 automatic model rerouting, item 20 as a shipped prompt library, signed release distribution, native MXC SDK integration, proof test staging into target test suites, base-branch policy loading with CI gate enforcement, and a benchmark runner with real corpus cases. No field finding was upgraded to confirmed in the rerun: a sandbox harness built from the drive mapping template line demonstrated the apostrophe breakout mechanically, but a generator-level proof through the real application remains the bar for confirmation.

## Field run 2026-10-23: third party macOS updater with a root helper (Swift)

A full six phase run against a public macOS app updater (74 files, SwiftPM packages plus a root LaunchDaemon helper over XPC). Two isolated hunters, independent Blue verification, sandbox proofs, one separate evaluator pass. Final adjudicated result: 0 confirmed, 10 needs validation, 3 rejected. The first Blue pass overclaimed two confirmations; the evaluator demoted both (the executed harness is not the project's test runner, and the title claimed a root rung the run itself listed as unproven), overturned one postinstall record as defense-in-depth rather than a finding, and surfaced two missed records that were then added. That correction loop is the strongest evidence yet that the separate evaluator (item 12, still manual) is load-bearing. Details stay in the private run directory pending disclosure to the maintainer. What OMGS learned:

1. The Red and Blue split earned its keep twice in one run. Blue sandbox tests killed two plausible hunter candidates: a claimed zip extraction escape and setuid preservation through the exact `ditto -x -k` flags the helper uses (entries sanitized, setuid stripped), and a claimed verified-download swap that the helper's root-owned staging plus independent revalidation already contained. Rejected records with counterevidence are now a visible strength of the report, not an edge case.
2. Tier 1 proof on a non-web stack needs a documented fallback. `swift test` cannot run inside the Seatbelt profile: SwiftPM invokes a nested sandbox that is denied, and both build systems then fail with I/O errors. What worked was compiling the unmodified target modules with `swiftc -emit-library` and running the same invariant assertions through a small harness inside `omgs prove`, with the XCTest file kept as the proposed regression test and the runner substitution disclosed in evidence. The skill should ship this recipe for Swift targets instead of leaving each run to rediscover it.
3. Seatbelt does not contain daemon mediated effects. A `defaults write` inside `omgs prove` landed in the real user preference domain through cfprefsd, outside the scratch area. Proof guidance must warn that preference, launchd, and similar daemon IPC escapes file based containment: use throwaway domains, verify deletion after the run, or avoid the API. `NSTemporaryDirectory()` also resolves to the real per-user temp dir under the sandbox; harnesses must use scratch relative temp paths. Superseded (2026-10-24): the "verify deletion after the run" option is wrong, because the escaping write has already hit the host; such daemon-mediated APIs must be avoided in the proof or the record left `needs_validation`, never relied on with post-run cleanup. See skill/VALIDATION-AND-REPORTING.md.
4. Ledger seeding is still too coarse for privileged targets. A repo with a root helper got one whole-repo unit (`stack:swift`) with four attack classes. Seed per-boundary units when privileged components exist: XPC service surface, installer, download and resolver chain, policy loading, packaging scripts.
5. Report renderer: the "Needs your intent" section repeats the full evidence of every needs-validation record, including ones with no intent question, doubling a 26 KB report with duplicated prose. That section should list only records that carry an intent question, and evidence paragraphs need basic structure (short trace list, then sandbox result) instead of single wall-of-text paragraphs.
6. Hunter output needs a machine readable contract. Two hunters returned about 25 free-form candidates that Blue merged into 11 records by hand, and long hunter reports were truncated in transit and had to be recovered from session logs. Hunters should write schema-shaped candidate files into the run directory (plus a short prose summary), so deduplication and fingerprinting are mechanical.
7. Run metadata is still on the honor system (reaffirms item 19): hunter, verifier, and agent call counts stayed null through a complete run because no CLI step asks for them. `omgs report` should warn or fill them from flags.
8. Sensor coverage gap reaffirmed: only gitleaks ran. A Swift capable sensor (semgrep was unavailable on the host) would have seeded at least the text-parsed identity check candidate mechanically.
9. Skill framing is stale: SKILL.md still introduces itself as a Next.js App Router review. The packs and CLI handled a Swift privileged-helper target well, so the description and phase text should go stack agnostic where the method already is.

Follow-up the same day: the manual validation plans for the root-helper records were executed on a dedicated sacrificial Mac (Gatekeeper off, passwordless sudo, synthetic Developer ID signed but unnotarized probe fixtures). A nil expected signing team disabled team verification and ran the probe package's postinstall as root; the package path bound neither bundle identifier nor version; and an older payload installed over a newer one with the expected version never enforced. Two symlink-handling leads (a dmg app symlinked outside the image, and a destination that is itself a symlink to an out-of-tree victim) were refuted: the helper replaced the symlink atomically and never wrote through it. The reproducer shapes and proofs are recorded in [benchmark/field-cases.md](benchmark/field-cases.md) as candidates 4 to 6 plus rejected leads. Two process lessons: (a) a dedicated-host manual proof is a distinct, lower-portability tier than `sandbox_exploited` and must be labelled as such, so a stack-agnostic skill needs a documented recipe for proofs that cannot run inside the OS sandbox at all; (b) the driver that loaded the target modules linked the helper library by bare leaf name and resolved it only through the working directory, which silently aborted every case on the first pass and produced false "refused" results until the load path was fixed. A harness that crashes before reaching the code under test must fail loudly, never be read as the target refusing the operation.

Correction and remediation (2026-10-23): the machine used for that manual proof was not sacrificial. It is a productive Mac with real data and Keychain access, so running elevated installer proofs there (Gatekeeper disabled, passwordless sudo added) was a safety mistake and a breach of the sandbox-only invariant. The machine was then restored: Gatekeeper re-enabled (`spctl --status` = assessments enabled), the `NOPASSWD` sudoers drop-in removed, the root-owned test app and the `com.example.probe` receipt deleted. The durable fix is to make the exception safe by construction, not by discipline: the new `dedicated_host` proof tier (tier 3) requires a disposable-host attestation in `prerequisites`, `omgs validate` rejects a `dedicated_host` record without one, and the guidance now says tier 3 runs only on a throwaway VM or wiped machine with no real data or credentials, snapshotted and discarded. Any host weakening (Gatekeeper off, passwordless sudo) is part of the attestation and must be reverted. Items implemented from this run: the `dedicated_host` tier and attestation rule; stack-agnostic SKILL framing (item 9); the non-web/Swift proof recipe and sandbox-escape warnings in validation guidance (items 2 and 3); per-boundary ledger seeding for privileged targets (item 4); the machine-readable hunter candidate schema (item 6); run-metadata flags and rendering with a warning when absent (item 7); and an optional offline semgrep sensor (item 8). Item 5 (intent section and structured evidence) and the `family` field were already present.

Correction (2026-10-24, from the second GPT-6.1-Sol review): the `dedicated_host` proof tier was removed, not kept. A tier whose decisive step runs outside `omgs prove`, with no backend that enforces it, cannot satisfy the sandbox-only invariant no matter how the host is framed, and the attestation check (non-empty `prerequisites`) was trivially satisfiable. The model is back to three tiers (`traced`, `test_proven`, `sandbox_exploited`). An effect the sandbox cannot contain (real root, Gatekeeper, a root helper) now has no tier and stays `needs_validation` with a manual plan; a live VM demonstration is a manual step outside OMGS, for severity only, never required. The semgrep sensor also gained `--strict`, an explicit check of the JSON `errors` array (a nonempty array or unparseable output marks the scan incomplete rather than a clean zero-hit run), and a fail-closed path when a configured local ruleset cannot be canonicalized.

Sandbox hardening (2026-10-24, from an automated scan of the committed tree): the proof backends were tightened. Seatbelt now denies, by name, the daemons that let sandboxed code mutate the host out of band (cfprefsd, LaunchServices/coreservicesd, distributed and local notifications, mDNSResponder, AppleEvents) and denies mach-register, on top of the existing network and non-scratch-write denials; this closes the observed cfprefsd write escape while keeping broad file-read and process-exec that arbitrary builds need. A full deny-by-default profile was not adopted because it breaks the compiler the proof step depends on; denying the escape-enabling services is the pragmatic equivalent and was verified against the Swift fixture. The sandboxed command now runs as its own process-group leader and a timeout signals the whole group, so grandchildren cannot survive or hold the output pipes open. The source walk no longer follows symlinked directories (it reads the directory entry type instead of resolving the link). The bubblewrap path gained namespace isolation (--unshare-all, --new-session, --die-with-parent) and tmpfs masks over /tmp, /run, and /var/run; narrowing its broad read-only root bind to an explicit path set is deferred because it needs validation on a real Linux host, which was not available. Remaining gap to track: a true deny-by-default profile on both backends, and the narrowed Linux bind set.

Proof supervision and bubblewrap (2026-10-24, from a scan of the hardening commit): `run_with_timeout` now terminates the command's whole process group on every exit path (normal, error, timeout), not only on timeout, so a command that backgrounds a child and exits cannot leave code running or hold the output pipes; output is drained through a bounded channel read, and the group kill is skipped for backends that did not create a group (MXC). The bubblewrap re-bind of the target after the tmpfs masks is now guarded so it cannot re-expose a masked directory (it is skipped when the target path is itself `/`, `/tmp`, `/run`, `/var/run`, `/dev`, or `/proc`). Two residuals are tracked, not yet fixed: (a) on the normal-exit path the leader is reaped by `try_wait` before the group is signalled, leaving a microsecond pid/pgid-reuse window; the clean fix is a peek-without-reap (`waitid` with `WNOWAIT`), which `nix` does not wrap on macOS and `waitpid` does not support there, so it needs raw per-platform `waitid`/`siginfo` wiring validated on both macOS and Linux; (b) the deny-by-default Seatbelt profile and the narrowed Linux bubblewrap bind set, as noted above.

Detached descendants and capture completeness (2026-10-24, from the fourth review): the group signal now uses `libc::kill` with a negative pid (direct syscall, no `/bin/kill` helper), always follows with a `child.kill()` fallback, and reaps with a bounded loop. Incomplete output capture is no longer reported as success: if both pipe ends do not close within the drain deadline, a descendant retained them and the run returns failure with a note. The irreducible macOS limitation is a descendant that calls `setsid()` and redirects its pipes: it leaves the process group, so the signal misses it, and it closes our pipes, so capture completes. Such a survivor stays confined by the Seatbelt profile (writes only to scratch, network denied) and cannot escape to the host, but it can outlive the proof. The Linux backend already closes this: `--unshare-all` includes `--unshare-pid`, so the kernel reaps all descendants when the namespace init exits. Fully closing it on macOS needs a stronger containment primitive (a PID-namespace-equivalent or the MXC executor's process containment) and is tracked, not yet implemented.

## Multi-agent pipeline is now the default (2026-10-24)

A full multi-agent run against a public macOS updater with a root helper (details held privately pending maintainer disclosure) was compared head to head with a single static reading pass over the same target. The single pass produced only traced, all-open records and read as thin. The multi-agent pipeline (three isolated red hunters, one per boundary, in separate contexts; an independent blue verifier that deduped by fingerprint and adversarially disproved; tier-1 sandbox proofs on unmodified target code via `omgs prove`; and a separate evaluator adjudication) produced about 21 raw candidates deduped to 12 records: 0 confirmed, 8 needs_validation, 4 rejected, with 3 test_proven mechanisms. It both found sharper, genuine issues the static pass missed (a local privilege-escalation chain and two sandbox-proven symlink staging-isolation breaks) and independently rejected four weak leads with counterevidence. The evaluator caught the one subtle labeling question (a mechanism can be test_proven while the end-to-end claim stays needs_validation) and sharpened a weak-gate characterization.

Decisions taken from this:
1. The phase flow in SKILL.md is now stated as a multi-agent pipeline by default: red hunts in isolation, blue verifies independently, a separate evaluator adjudicates, green proposes fixes, each in its own fresh context. A single combined pass that hunts, verifies, and reports in one context is explicitly not an OMGS review. The separate evaluator (previously item 12, "still manual") is now a first-class phase (Adjudicate), because it is where overclaimed confirmations and mislabelled proofs are caught.
2. An optional live-progress view ships as a reference under `skill/progress/` (a self-contained offline `dashboard.html` plus a `status.schema.json` the orchestrator writes at each milestone). It never changes a verdict; the deterministic `findings.json`/`REPORT.html` remain the record. If served it binds loopback only and shuts down at the end; it never auto-opens a browser and never binds a non-loopback interface, because it describes vulnerabilities.

Still planned (tracked, not yet done):
- Fold a pipeline and coverage timeline into `REPORT.html` so the methodology (which agents ran, timings, what was examined) is preserved in the deterministic artifact, not only in the ephemeral progress view.
- Populate the benchmark corpus with real post-cutoff CVE pairs and publish recall, false positives, cost, and variance, so "best in class" rests on numbers rather than description.
- Consider a `--watch` convenience in the skill that stands up the loopback progress server and tears it down with the run.
